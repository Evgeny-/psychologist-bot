# Глубокий отчёт по дневнику

Методика воспроизведена по реальному прогону (дневник за ~4 месяца, 158 записей). Все скрипты в `scripts/` универсальны и не содержат персональных данных - персональное содержимое живёт только во временных файлах в scratchpad-директории, которые никогда не коммитятся и не попадают в этот скилл.

**Репозиторий публичный.** На каждом шаге ниже: никаких имён, дат конкретных жизненных событий, ID телеграм-каналов/групп, IP/hostname/путей на сервере, кредов. Всё это - либо в scratchpad (не в репо), либо за плейсхолдерами вида `{событие N}`.

## Обзор пайплайна

1. Дамп продовой SQLite-базы с сервера в scratchpad.
2. Экспорт нужных таблиц в JSON (`scripts/export.sh`).
3. Группировка записей по ISO-неделям (`scripts/batch-weeks.mjs`).
4. Выжимка каждой недели отдельным субагентом, параллельно.
5. Подсчёт количественных метрик (`scripts/compute-stats.mjs`).
6. Сборка дайджеста из недельных выжимок для финального анализа.
7. Финальный психологический анализ пишет основная модель (не субагент).
8. Рендер HTML-артефакта с графиками (`scripts/report-template/gen.mjs`).
9. Проверка по чек-листу подводных камней перед показом пользователю.

Все промежуточные файлы (дамп базы, экспорт, батчи, выжимки, дайджест, `report.html`) кладутся в scratchpad-директорию текущей сессии, а не в репозиторий.

## Шаг 1. Дамп базы с сервера

На сервере нет `sqlite3` CLI, а база работает в WAL-режиме - простое копирование `.db`-файла (`cp`/`scp` напрямую) может потерять недавно записанные данные, которые ещё лежат в `-wal` файле. Правильный способ - сделать консистентный бэкап через `better-sqlite3` прямо в Node.js на сервере:

```bash
ssh <server> 'cd ~/cbt-bot && node --input-type=module -e "
import D from \"better-sqlite3\";
const db = new D(\"data/cbt-bot.db\", { readonly: true });
await db.backup(\"/tmp/cbt-dump.db\");
console.log(\"done\");
"'
```

Затем скачать дамп локально и убрать временный файл с сервера:

```bash
scp <server>:/tmp/cbt-dump.db "$SCRATCHPAD/cbt-dump.db"
ssh <server> 'rm -f /tmp/cbt-dump.db'
```

SSH-реквизиты - в локальном файле оператора вне репозитория (см. AGENTS.md, он git-ignored). Не запрашивай и не записывай хост/логин/ключи в код скилла, в промпты субагентам или в артефакт.

## Шаг 2. Экспорт таблиц в JSON

Локально (не на сервере) через `sqlite3 -json`:

```bash
scripts/export.sh "$SCRATCHPAD/cbt-dump.db" "$SCRATCHPAD/export"
```

Экспортирует:
- `entries.json` - id, date, local_time, type, text (`COALESCE(transcript, raw_text)`), duration_seconds, source;
- `analyses.json` - entry_id, sentiment, emotions_json, triggers_json, wins_json, topics_json, distortions_json, orbit_themes_json, gratitude_count;
- `metrics.json` - entry_id, date, mood, anxiety, stress, productivity, routine;
- `daily_memory.json`, `memory.json` - вспомогательные таблицы бота.

Колонки `source` и `orbit_themes_json` появились не сразу, поэтому скрипт сначала проверяет
их наличие через `pragma_table_info` и подставляет в SELECT только если они есть - на старой
базе экспорт всё равно отработает.

`source` важен: в базе рядом с живым дневником может лежать импортированный архив
(`source='archive'`), и без фильтра KPI посчитаются по обоим корпусам сразу. Фильтрует
`compute-stats.mjs` (шаг 5), а не экспорт - в текстовые батчи архив тоже иногда нужен.

Все эти файлы содержат сырое содержимое дневника - держи их только в scratchpad.

## Шаг 3. Батчи по неделям

```bash
node scripts/batch-weeks.mjs \
  --entries "$SCRATCHPAD/export/entries.json" \
  --analyses "$SCRATCHPAD/export/analyses.json" \
  --out "$SCRATCHPAD/batches"
```

Группирует записи по ISO-неделям (понедельник-воскресенье), склеивает каждую запись с её анализом (sentiment/emotions/topics/distortions/wins) и пишет:
- `batches/week-01.json`, `week-02.json`, ... - по одному файлу на неделю, пронумерованы по порядку появления данных (не по номеру недели в году);
- `batches/index.json` - манифест `[{ file, week, from, to, count, chars }, ...]`.

## Шаг 4. Выжимки по неделям (субагенты)

Один субагент Sonnet-уровня на неделю, все недели - параллельно (несколько вызовов Agent/Task в одном сообщении). Каждый агент:
1. читает свой `batches/week-NN.json`;
2. пишет результат в `summaries/week-NN.json` **сам, через Write**, до завершения - не полагайся на то, что оркестратор сохранит из ответа агента.

Готовый шаблон промпта (подставь `{WEEK_FILE}` и `{SUMMARY_FILE}` на конкретные пути в scratchpad):

```
Ты анализируешь один фрагмент личного дневника (одна календарная неделя) для
глубокого психологического отчёта. Источник: {WEEK_FILE} - JSON с массивом
entries, у каждой записи есть text, date, local_time, type и уже посчитанные
ботом sentiment/emotions/topics/distortions/wins.

Прочитай файл полностью. Верни СТРОГО валидный JSON (и сохрани его в
{SUMMARY_FILE} через Write) со структурой:

{
  "week": "<номер недели из входного файла>",
  "entrySummaries": [
    {
      "entry_id": <id>,
      "date": "<дата>",
      "summary": "<2-4 предложения о том, что произошло и что важно>",
      "key_events": ["<конкретные факты/события>", "..."],
      "emotions": ["<эмоции, которые реально звучат в тексте>", "..."],
      "themes": ["<темы>", "..."],
      "tone": "positive" | "neutral" | "negative" | "mixed"
    }
  ],
  "weekOverview": {
    "narrative": "<связный абзац о неделе в целом>",
    "emotional_arc": "<как менялось состояние в течение недели>",
    "relationship": "<если есть материал - иначе пусто>",
    "work": "<если есть материал - иначе пусто>",
    "health_habits": "<сон/спорт/еда/рутина, если упоминаются>",
    "cbt_patterns": ["<когнитивные искажения и паттерны мышления с привязкой к конкретным записям>"],
    "wins": ["<реальные победы недели>"],
    "struggles": ["<реальные трудности недели>"]
  }
}

Требования:
- Пиши по-русски.
- Сохраняй конкретику: имена, числа, даты, факты - не обобщай и не сглаживай.
  Это единственный источник, из которого финальный анализ узнает детали этой
  недели - если ты потеряешь конкретику здесь, она пропадёт из отчёта совсем.
  ("Единственный источник" здесь означает: финальный анализ читает только
  выжимки, а не сырые записи, - так что не спрямляй углы.)
- Не приукрашивай и не давай терапевтических советов - это задача следующего
  шага, твоя - точная и честная выжимка.
- Обязательно сохрани файл через Write, прежде чем завершить работу - твой
  текстовый ответ оркестратору не читается напрямую.
```

Если оркестрируешь через Workflow/Task-инструмент, который параллелит список
недель: передавай список недель **литералом прямо в коде/промпте**, а не
через параметры `args` - `args` может прийти в оркестратор строкой целиком
(например, `"1,2,3"` вместо массива), и цикл по нему молча отработает не так,
как ожидалось.

### Тематические агенты поверх понедельных выжимок

Понедельные выжимки дают хронику, но хроника - это ещё не разбор. На прогоне за полгода
заметно больше дал второй, параллельный слой: **агенты сильной модели, каждый читает
ВЕСЬ корпус целиком под своим углом**, а не одну неделю. Веди оба слоя одновременно:
недельные - на быстрой модели, тематические - на сильной.

Углы, которые окупились (по одному агенту на пункт):

- **скрининг** - доказательная база по диагностическим критериям, «за» и «против» с датами, отдельно сплошной поиск по маркерам риска;
- **форензика искажений** - не частоты, а замкнутые контуры «триггер → мысль → поведение → подтверждение» и глубинные убеждения словами самого автора;
- **«почему нет сдвига»** - разрыв «намерение → действие», что реально сработало и при каких условиях;
- по одному агенту на **крупную линию жизни** (отношения / работа / тело и режим);
- **ресурсы** - форензика хороших дней: что им предшествовало, разобрать каждый день выше порога;
- **последний месяц** под микроскопом, день за днём;
- **архив** (если есть корпус до начала дневника) - отвечает на вопрос «это эпизод или так было всегда», на который свежий период ответить не может.

Три вещи, без которых этот слой не работает:

1. Файлы большие; агенту надо явно сказать читать их кусками через `sed -n` и указать, что куски существуют (`split -b 170000 -d файл part_`), иначе он прочитает первые 25k токенов и остановится.
2. Требовать дату и дословную цитату на каждое утверждение - иначе получается пересказ.
3. Просить сохранять результат через Write в отдельный файл и **не** полагаться на текстовый ответ.

Практический потолок - 20 одновременных субагентов; планируй волнами и учитывай, что
агент может запускать собственных детей и занимать несколько слотов.

## Шаг 5. Метрики

```bash
node scripts/compute-stats.mjs \
  --entries "$SCRATCHPAD/export/entries.json" \
  --analyses "$SCRATCHPAD/export/analyses.json" \
  --metrics "$SCRATCHPAD/export/metrics.json" \
  --out "$SCRATCHPAD/export/stats.json"
```

Считает (полная схема - в комментарии в начале файла):
- дневные ряды `mood`/`anxiety`/`stress`/`productivity`/`routine` (среднее по дню, если записей несколько);
- помесячные средние по тем же метрикам + число дней с записями в месяце;
- распределение sentiment (positive/neutral/negative) по месяцам;
- топ тем/эмоций/искажений - парсинг `*_json` полей, нормализация, подсчёт частоты;
- `distortionsByMonth` - те же искажения в разбивке по месяцам;
- `orbits` / `orbitsByMonth` - повторяющиеся темы; **`orbits` считается в уникальных ДНЯХ**, а не в записях: тема, упомянутая пять раз за один день, - это один день темы, и именно дни делают «сколько раз я к этому возвращаюсь» читаемым;
- `monthlyVolume` - записей / дней / знаков по месяцам; это база нормировки для графика динамики искажений;
- число "побед" (`wins_json`) по неделям и суммарно;
- распределение записей по часам суток и по дням недели;
- сумму `gratitude_count`;
- KPI: число записей, покрытие дней, лучший стрик, число слов, минуты голосовых записей.

Две вещи, на которых этот шаг ломается молча:

- **`distortions_json` бывает двух форм.** Старые строки - массив строк, новые - массив объектов `{type, quote, reframe}`. Скрипт берёт `type` в обоих случаях. Плюс склеивает вариантные написания одного паттерна (`Долженствование` и `Долженствование ("надо было")` - это один паттерн, а не два), иначе топ рассыпается на синонимы.
- **Архивные записи отфильтровываются по умолчанию.** Строки с `source != 'live'` исключаются вместе с их анализами и метриками; в конце скрипт печатает, сколько выкинул. Флаг `--include-archive` возвращает их обратно - нужен, только если отчёт сознательно про весь корпус.

7-дневное скользящее среднее **не** хранится в `stats.json` - оно считается на лету в `gen.mjs` из дневного ряда (это забота отрисовки, а не факт-таблицы).

## Шаг 6. Дайджест для финального анализа

Склей все `summaries/week-NN.json` (`weekOverview` + `entrySummaries`) в один markdown-файл в scratchpad, по неделям в хронологическом порядке. На реальных данных (~4 месяца) дайджест выходит порядка 150-250 тыс. знаков.

Читай его частями по 70-80 строк за раз - инструмент Read усечёт отдельные строки длиннее ~2000 символов и весь файл, если он превышает ~25k токенов за один вызов. Это ожидаемо и не является потерей данных - просто читай последовательными кусками, пока не пройдёшь весь файл.

Перед сборкой дайджеста проверь, что для каждой недели из `batches/index.json` существует соответствующий `summaries/week-NN.json` - если субагент не сохранил файл (см. шаг 4), эта неделя выпадет из финального анализа молча.

## Шаг 7. Финальный анализ

Пишет **основная модель**, а не субагент - после того как она прочитала весь дайджест целиком (по частям, как в шаге 6). Единственный источник фактов для этого шага - недельные выжимки; сырые записи из `entries.json` в анализ не подаются.

Обязательная структура отчёта:
1. хроника по месяцам;
2. чтение метрик - тренды, расхождения между шкалами (mood/anxiety/stress/...) и тем, что видно в тексте;
3. сильные стороны;
4. центральные паттерны - как они сцепляются друг с другом в один контур;
5. разбор топ когнитивных искажений с цитатами (перефразированными, без личных данных третьих лиц вне контекста самого пользователя) и противоядиями;
6. деликатные темы (отношения) - бережно и прямо, без ухода в общие фразы;
7. работа;
8. здоровье;
9. экзистенциальный слой;
10. список достижений;
11. приоритизированный план на 90 дней.

Тон: честный, тёплый, без сюсюканья, на «ты».

## Шаг 8. HTML-артефакт

Генератор графиков - `scripts/report-template/gen.mjs`. Модель отдельно пишет `prose.html` (текст отчёта из шага 7, размеченный HTML) с плейсхолдерами, которые `gen.mjs` заменяет на инлайн-SVG графики:

- `{{KPI_ROW}}` - плашки с ключевыми показателями;
- `{{CHART_MOOD}}` - настроение по дням + скользящее среднее;
- `{{CHART_SMALL_MULTIPLES}}` - тревога/стресс/продуктивность/режим дня;
- `{{CHART_SENTIMENT}}` - тон записей по месяцам (расходящаяся диаграмма);
- `{{CHART_DISTORTIONS}}` - топ когнитивных искажений;
- `{{CHART_HOURS}}` - время записей по часам суток;
- `{{CHART_WINS}}` - "победы недели" по неделям;
- `{{CHART_MONTHLY_MOOD}}` - среднее настроение по месяцам, столбики (худший месяц выделен);
- `{{CHART_ORBITS}}` - повторяющиеся темы, ранжированные по числу разных дней;
- `{{CHART_DISTORTION_TREND}}` - топ-6 искажений по месяцам, small multiples, **нормировано на 10 записей месяца** (в сырых числах график просто повторил бы, в каком месяце больше писали).

Последние три читают поля, которых может не быть в старом `stats.json`; тогда каждый из них отдаёт пустую строку, и `prose.html` можно писать, не проверяя наличие данных.

Русские подписи тем в `{{CHART_ORBITS}}` продублированы в `gen.mjs` константой `ORBIT_LABELS`; источник истины - `src/prompts/orbits.ts`. Незнакомый ключ рисуется как есть, так что расхождение таксономии деградирует мягко.

`prose.html` не входит в этот скилл - он пишется заново под каждый отчёт и никогда не коммитится (в нём персональный текст).

Перед запуском `gen.mjs` открой файл и, если хочешь подписать конкретные периоды/события на графике настроения, заполни в его начале массивы `BANDS` и `EVENTS` **плейсхолдерами**, а не реальными названиями:

```js
const BANDS = [['2026-04-17', '2026-05-03', '{период 1}']];
const EVENTS = [['2026-05-12', '{событие 1}', 1]];
```

Запуск:

```bash
node scripts/report-template/gen.mjs \
  --stats "$SCRATCHPAD/export/stats.json" \
  --prose "$SCRATCHPAD/report/prose.html" \
  --out "$SCRATCHPAD/report/report.html" \
  --title "Дневник · отчёт за период"
```

Графики: светлая и тёмная тема через CSS-переменные (`prefers-color-scheme` + `data-theme` override), линии 2px, hairline-сетка, подписи значений прямо на графике, таблицы-дублёры данных в `<details>`, тултип на линии настроения.

Блок `css` в `gen.mjs` - **отправная точка, а не фирменный стиль**: палитра и шрифты в нём заданы нейтрально, и под конкретный отчёт их нормально переопределить (скопируй `gen.mjs` в scratchpad и правь копию). Важно сохранить структуру темизации - полный набор токенов в голом `:root`, переопределение только токенов в `@media (prefers-color-scheme: dark)` под guard'ом `:root:not([data-theme="light"])` и ещё раз в `:root[data-theme="dark"]` - и имена классов, которые генератор проставляет в SVG (`tick`, `val`, `axis-label`, `band-label`, `event-label`).

Готовый `report.html` публикуй через инструмент Artifact (он приватный по умолчанию - делиться пользователь решает сам). В артефакт не включай сырые записи дневника - только агрегаты и текст финального анализа.

## Шаг 9. Чек-лист подводных камней

- База в WAL-режиме - копировать файл напрямую нельзя, только `db.backup()` (шаг 1).
- `distortions_json` бывает и массивом строк, и массивом объектов `{type, quote, reframe}`; если считать только строки, топ искажений выйдет пустым (шаг 5).
- В `entries` рядом с живым дневником может лежать импортированный архив - без фильтра по `source` KPI посчитаются по обоим корпусам (шаг 5).
- На сервере нет `sqlite3` CLI - JSON-экспорт делается локально, после скачивания дампа.
- Если оркестрируешь субагентов по неделям через Workflow-инструмент - список недель передавать литералом в коде, не через `args` (может прийти строкой).
- Read усекает файлы больше ~25k токенов и строки длиннее ~2000 символов - дайджест для финального анализа читать последовательными кусками (шаг 6).
